# 记录、确认与维护

用户侧只需要表达和核对；以下参数由 Agent 根据明确上下文填写。

## 记录什么

| kind | 用途 | 必要内容 |
|---|---|---|
| decision | 已确认项目取舍 | 项目、内容、原因、范围、来源 |
| experience | 实践方法与教训 | 项目、内容、实际结果、适用条件、来源 |
| preference | 用户明确的长期要求 | 内容、主题 key、范围、来源 |
| correction | 纠正同主题旧要求 | 沿用原 key、新内容、范围、来源 |
| withdrawal | 撤销同主题要求 | 沿用原 key、撤销内容、范围、来源 |

所有记录带工具和日期。项目决定和经验先放项目中，不自动变成全局规则。原因或结果缺失时只问关键缺口，不能替用户生成“真实经历”。AI 推断不进入已确认状态。

## 写入流程

1. 调用 record_memory.py 保存待处理内容并追加收件箱回执。
2. 如果用户刚刚明确说“记住这个决定/以后按这个要求”，本次授权已覆盖准确内容，不重复问。资料导入、模型提炼或存在冲突时，先让用户集中核对。
3. 用 apply_memory.py --dry-run 看受影响文件；内容已确认时带 --confirmed 应用。
4. 应用同时更新正式页面、项目索引、启动卡的确认摘要和历史记录。旧卡中的手写内容保留，新确认区块明确覆盖同主题旧摘要。

同主题以记录时间选择当前要求，补处理旧记录不会覆盖新纠正；如果用户现在重新启用旧要求，记录一条新的明确表态。同时间的互相矛盾记录先集中核对，不猜先后。
5. 成功后说记到哪里；失败不能说已完成。已有相同 ID 重跑不会重复沉淀。

代码使用原子锁，忙时返回 75，留在当前任务等待或重试，不删除其他任务的锁，不把失败说成成功。锁可能因进程中断留下；先核对任务是否结束，再由用户授权恢复，不只因“过了两小时”就抢占。

## Agent 内部命令示例

~~~bash
python3 scripts/record_memory.py --vault <库路径> --kind decision --project <项目名> --scope project --key <决策主题> --summary <已确认决定> --reason <用户确认的原因> --agent <工具名> --source <用户原话或文件行号>
python3 scripts/record_memory.py --vault <库路径> --kind experience --project <项目名> --scope project --key <方法主题> --summary <方法或教训> --result <实际结果> --conditions <适用条件> --agent <工具名> --source <依据>
python3 scripts/apply_memory.py --vault <库路径> --record <记录ID> --dry-run
python3 scripts/apply_memory.py --vault <库路径> --record <记录ID> --confirmed
~~~

用户不需要输入这些命令。不要把私人原文或凭据塞进可公开分享的命令记录。

## 整理与复盘

先列收件箱及 00-索引/待处理 的记录，通过 00-索引/.已确认记录.json 判断哪些尚未应用。已经确认的可以应用；未确认或矛盾条目集中核对。

不要清空整个收件箱：整理途中可能有新记录。保留记录 ID 和待处理原文，用已确认状态判断消费完成；需要归档时只处理明确列入本次范围的记录。

原始会话只能在用户授权范围内提取。文件不可读、接口失败就留下缺口，不从标题补故事。

周复盘可总结、合并和检查已确认内容，保留用户自写内容及受管理区块。摘要整理后运行：

~~~bash
python3 scripts/apply_memory.py --vault <库路径> --refresh
~~~

这会根据已有确认索引重建正式视图及启动卡管理区块，不把未经确认的推断提升进去。已确认全局主题都出现在卡的更新区块，最近项目摘要按范围标记；卡过长时精简人工摘要并保留正式索引，不能把新要求默默丢掉。

## 兼容已有库

旧库可继续读。接入不会整体替换手写内容。新记录使用本 Skill 的记录/应用流程；旧收件箱行保留，整理时从原文提炼候选再核对。新增脚本只维护带自身标记的区块，不覆盖其他内容。
